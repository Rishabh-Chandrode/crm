# Extension Source — Agentic Coding Rules

These rules apply to all TypeScript source files within `packages/extension/src/`.

---

## Rules (ENFORCED)

### Working with `popup.ts` (CRITICAL — it's large)
1. **ALWAYS search for the relevant function/section before editing.** This file is ~65KB. Do NOT read the entire file — search for the specific function name, event handler, or UI section.
2. **Sections are organized by tab/feature.** Look for comment headers like `// === Tab Name ===` or function names matching the feature.
3. **DOM manipulation patterns:** The popup uses raw DOM — `document.getElementById()`, `classList.toggle()`, `innerHTML`. No framework.
4. **State is stored in `chrome.storage.local`.** Auth token, backend URL, and user preferences are persisted there.

### Build Process
1. **After ANY `.ts` file change, run `pnpm build`** (or rely on the watch process `pnpm dev`).
2. **Never edit `dist/` files.** They are generated by esbuild from `build.mjs`.
3. The build entry points are defined in `build.mjs`. If you add a new TypeScript entry point, register it there.

### Type Sync
- `types.ts` mirrors relevant interfaces from `packages/backend/src/types/index.ts`.
- Extension may use `camelCase` field names where data comes from DOM scraping. Conversion to `snake_case` happens at the API boundary (before sending to backend).

### Chrome APIs
- Use `chrome.runtime.sendMessage()` for inter-context communication.
- Use `chrome.storage.local` for persistent state.
- Use `chrome.sidePanel` for side panel management (registered in `background.ts`).
- All new permissions must be added to `manifest.json` with justification.

### Automated Testing (ENFORCED)
- All new logic, DOM parsers, and messaging interfaces must have unit tests in `src/__tests__/`.
- Run `pnpm test` in this package (`vitest run`) and ensure all tests pass before completing changes.
